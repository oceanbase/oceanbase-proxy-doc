## V4.3.1

### Version information

* Release date: July 1, 2024

* Version: V4.3.1

* RPM version: obproxy-4.3.1.0-402024062810

### Version location

ODP V4.3.1 is a long-term support (LTS) version in the ODP 4.3.x series. We recommend that you use this version for POC testing and production in cloud and on-premises environments. The SQL proxy has added automatic primary-standby database routing, multiple zone routing, ASCII character set routing, and utf8mb4_0900_ai_ci collation routing. It also supports the binlog_service_ip parameter for domain names and multiple addresses. In addition, the routing strategy has been optimized for single-node deployment scenarios, significantly improving performance. The RPC proxy has added the HBase Empty Family feature, improved the ObTableLSOps request types, and optimized the request protocol parsing logic and batch retrieval mode for routing information.

### Key features

#### SQL proxy

##### Automatic primary-standby database routing

In OceanBase Database 2.x/3.x, a CLUSTER_NAME corresponds to a group of primary and standby clusters. When you log in, you connect to the primary cluster by default. If a primary-standby switch occurs, the ODP automatically routes to the new primary cluster, and the CLUSTER_NAME remains unchanged, so no modifications to the login connection string are required. In OceanBase Database 4.x, to fully leverage the multi-tenant feature, physical standby databases are provided at the tenant level instead of the cluster level. The primary or standby role information belongs to the tenant, not the cluster. Two different tenants can be primary and standby to each other, and the primary-standby relationship is maintained by an external component (OCP).

After a primary-standby switch, the tenant name in the connection string must be modified for normal login, which affects the business. Starting from ODP 4.3.1, ODP interacts with the OCP interface to internally record the primary-standby relationship at the tenant level, associate different tenants, and manage the connection string using service_name. This shields users from tenant-level primary-standby awareness, achieving the same automatic primary-standby routing effect as OceanBase Database 2.x/3.x.

For more information about automatic primary-standby routing, see [Automatic primary-standby tenant routing](../../../600.data-routing/450.primary-and-backup-tenant-routing.md).

##### Multiple zone routing

The `proxy_primary_zone_name` parameter in ODP supports specifying a single zone for routing, directing all requests received by ODP to the specified zone. OceanBase Database supports mixed OLAP and OLTP workloads, requiring ODP to route analytical requests to multiple OLAP replicas for load balancing. Therefore, ODP V4.3.1 extends the `proxy_primary_zone_name` parameter to support multiple zone routing.

##### Character set and collation expansion

OceanBase Database 4.2.4 supports the ASCII character set, TIS620 character set, and utf8mb4_0900_ai_ci collation. ODP V4.3.1 also supports routing for these character sets and collations.

##### Domain name and multiple address support for binlog_service_ip

In the interaction architecture between the Binlog service and ODP, ODP first obtains the corresponding Binlog service cluster address through the binlog_service_ip parameter before sending a Binlog-related SQL request or a Binlog dump request to the specific Binlog service cluster. Currently, binlog_service_ip only supports a single IP address and does not support domain names, which is insufficient for high-availability scenarios. ODP V4.3.1 supports domain names and multiple addresses, enabling high availability in the following scenarios:

* Load balancing (LB) addresses have different physical IP addresses in different zones

* Automatic recovery capability during LB switching

##### Performance optimization

Single-node deployment mode: ODP is a dedicated service proxy for OceanBase Database, with the core goal of solving routing issues in distributed clusters with multiple nodes. The routing strategy has significant advantages in distributed scenarios, but in single-node scenarios, routing requirements are simple, and complex routing logic is unnecessary. Therefore, ODP 4.3.1 optimizes the routing logic for single-node scenarios, significantly improving routing performance.

Compilation optimization: ODP V4.3.1 introduces some system compilation optimizations, further enhancing performance.

In single-node mode, ODP V4.3.1 improves routing performance by 30% to 50% compared to ODP V4.3.0.

#### RPC proxy

##### Enhanced ObTableLSOps request functionality

ODP V4.3.0 introduced a new single-operation format and corresponding batch format to support the checkAndInsUp semantics and ObTableLSOps requests. ODP V4.3.1 further enhances this by supporting multiple TableOperations in LSOP requests, subrequest division based on log streams, and optimized performance.

##### HBase Empty Family

Currently, OceanBase Database's HBase API only supports single column families. To better support multiple column families and ensure compatibility without modifying client code in certain scenarios (such as when the client scan operation specifies an empty column family), the concept of table groups is introduced in HBASE mode. By default, an HBASE table corresponds to a table group in OceanBase Database, and an HBASE column family corresponds to a table in OceanBase Database. This approach is used to maintain compatibility with the HBASE column family concept. In this case, the table name in the request sent from the client to ODP corresponds to the current table group name. ODP must support routing at the table group level to enable the new HBASE mode.

### Configuration changes

|              Configuration item               | Change type |                                                                        Description                                                                        |
| --------------------------------- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| enable_single_leader_node_routing | New     | Controls whether to use more efficient routing rules when the tenant is deployed in a primary-replica cluster.                                                                                  |
| enable_full_link_trace            | New   | Controls whether to use full-link tracing to track query execution.  |
| rpc_max_response_batch_size       | New   | Sets the maximum number of batches sent in a single response.  |
| rpc_max_request_batch_size        | Changed  | The default value of this configuration item was updated from `5` to `20` starting from version 4.3.1.  |
| enable_standby                    | Changed     | Starting from version 4.3.1, this configuration item supports controlling whether to enable primary-standby tenant routing.                                                                                 |
| proxy_primary_zone_name           | Changed     | Starting from version 4.3.1, this configuration item supports configuring multiple zone names. |
| binlog_service_ip                 | Changed    | Starting from version 4.3.1, this configuration item supports configuring multiple IP addresses or domain names.   |
| enable_strict_stat_time           | Changed    | Starting from version 4.3.1, the default value of this configuration item was updated from <code>True</code> to <code>False</code>.   |
| proxy_mem_limited                 | Changed     | Starting from version 4.3.1, the value range of this configuration item was updated from <code>[100MB, 100G]</code> to <code>[100MB, +∞)</code>. |

### Supported OceanBase Database versions

OceanBase Database 4.x, 3.x, and earlier versions are supported. The recommended ODP version depends on the OceanBase Database version you use:

* If OceanBase Database is version 3.x or earlier, we recommend that you use ODP V3.2.11.

* If OceanBase Database is version 4.x, we recommend that you use ODP V4.3.1 (LTS).
