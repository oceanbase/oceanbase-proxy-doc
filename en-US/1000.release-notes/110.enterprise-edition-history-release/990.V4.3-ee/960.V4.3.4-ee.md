# ODP Enterprise Edition V4.3.4

## V4.3.4 hotfix1

### Version information

* Release date: May 26, 2025

* Version: V4.3.4 hotfix1

* RPM version: obproxy-4.3.4.0-332025052117

### Release purpose

To support the use of secondary partitioning and time-series table routing features in OBKV-HBase for OceanBase Database V4.3.5.2 and later versions.

### Bug fixes

* Fixed the issue where an exception error message was displayed when the table did not exist in OBKV.

* Fixed potential memory issues.

* Fixed the issue where an error occurred due to table deletion and reconstruction in OBKV.

## V4.3.4

### Version information

* Release date: April 18, 2025

* Version: V4.3.4

* RPM version: obproxy-4.3.4.0-262025041714

### Version overview

ODP 4.3.4 is the latest version in the ODP 4.3.x series. It is recommended for POC testing and production in both cloud and on-premises environments. The SQL proxy in ODP 4.3.4 supports routing for Asian character sets and collations, and allows functions to be used as partitioning keys. It also enhances core routing capabilities, optimizes routing strategies for replication tables and requests exceeding 4K, reduces remote routing, and improves routing performance. Additionally, it unifies global configuration items for protocols between ODP and OceanBase Database, enhancing protocol configuration usability. The RPC proxy in ODP 4.3.4 supports accurate routing for single-partition tables and atomic retrieval of partition information. It also enhances routing capabilities, improves congestion handling processes, and asynchronously retrieves ODP ls_id information to further improve system stability.

### Key features

#### SQL proxy

##### Enhanced routing capabilities

* Support for Asian character sets and collations

  ODP 4.3.4 fully supports Asian character sets, including ujis, euckr, cp932, and eucjpms, as well as their corresponding collations.

* Optimized routing for JOIN operations involving replicated tables

  In previous versions, ODP randomly routed requests to any OBServer node for replicated tables. If a replicated table was the first table in a JOIN operation, it could be routed to a non-replicated, non-leader node, resulting in remote routing and impacting overall performance. ODP 4.3.4 optimizes this by identifying the first table in a JOIN operation and using the joined table for routing, reducing remote routing and improving performance.

* Support for functions as partitioning keys

  Previously, ODP could not accurately calculate partitions when using function expressions as partitioning keys, leading to routing errors. ODP 4.3.4 addresses this by parsing and converting function expressions in partitioning keys, ensuring accurate partition calculations.

* Routing for requests exceeding 4K

  In versions prior to ODP 4.3.4, the `request_buffer_length` parameter had a default value of `4KB`. For requests exceeding 4KB that had not yet been parsed for routing information, ODP would randomly route them, potentially leading to remote routing and significant performance impact. To address this, ODP 4.3.4 increases the default value of `request_buffer_length` to `8KB`, ensuring accurate routing for requests exceeding 4KB.

##### Improved protocol configuration usability

ODP 4.3.4 introduces a new global configuration item, `server_protocol`, to explicitly control the protocol type between ODP and OceanBase Database. Previously, the protocols were adaptive and not controlled by configuration items, making it difficult to confirm the actual protocol type during troubleshooting. This new configuration item enhances protocol configuration usability by providing a clear and direct way to specify the protocol type.

#### RPC proxy

##### Enhanced routing capabilities

* Accurate routing for single-partition tables

  Previously, ODP could not accurately determine whether a table was partitioned or not, leading to potential routing errors when routing requests for single-partition tables through the RPC proxy. ODP 4.3.4 optimizes this by retrying routing based on error information provided by OBServer nodes, ensuring accurate routing for single-partition tables.

* Atomic retrieval of partition information

  Previously, ODP retrieved table information through multiple internal requests, which lacked atomicity and could lead to inconsistent table information. This could result in failed partition calculations. ODP 4.3.4 addresses this by adding real-time validation and retries for retrieved table information, ensuring accurate routing.

##### Enhanced congestion handling processes

ODP 4.3.4 supports asynchronous processing of RPC requests, isolating the request processing state machine from OBServer node network changes. This makes OBServer node status changes and congestion handling processes more independent. OBKV requests strictly depend on calculated partition and routing information for SQL forwarding, which can affect high availability. To ensure reliability, ODP 4.3.4 adopts strategies from the SQL proxy to handle congestion, ensuring that requests are never forwarded to faulty OBServer nodes.

##### Asynchronous retrieval of ODP ls_id information

Starting from ODP 4.3.1, the retrieval of ls_id information became synchronous and dependent on tablet_id retrieval, making SQL processing more complex and increasing pressure on the sys tenant of OceanBase clusters. ODP 4.3.4 addresses this by asynchronously decomposing the ls_id retrieval process and adding asynchronous tablet_id retrieval steps for LSOP requests.

### Supported OceanBase Database versions

ODP 4.3.4 supports OceanBase Database 4.x, 3.x, and lower versions. The recommended ODP version depends on the OceanBase Database version used:

* For OceanBase Database 3.x and lower versions, it is recommended to use ODP V3.2.11.

* For OceanBase Database 4.x, it is recommended to use ODP V4.3.1 (LTS version).

ODP 4.3.4 introduces several new features. If your environment relies on these new features, it is recommended to use the latest version, V4.3.4. If not, the LTS version, V4.3.1, is recommended.

### Bug fixes

* Fixed the issue where ODP could not connect to the read-only endpoint of the cluster on AWS.

* Fixed the issue where ODP failed to parse SQL statements following "--" when "--" was used in comments and the line was broken.

* Fixed the issue where DBMS_LOB.READ timed out and returned the business error `write clob error`.

* Fixed the issue where ODP failed to start in IPv6 mode on ARM.

* Fixed the issue where, in the case of a partitioned table with a missing partitioning key and a default partition, SQL requests were not randomly distributed as expected.

* Fixed the issue where, during a direct load, if a parameter was written incorrectly, the error `4016` was returned.

* Fixed the issue where, when user variables contained keywords such as `value`, the routing was inaccurate.

* Fixed the issue where, in a transaction, requests exceeding 4K in size failed to reconnect after parsing and retrying.

* Fixed the issue where, when OceanBase Database 2.0 and the compression protocol were disabled, no results were returned when using the PS protocol.

* Fixed the issue where, when the `kill query sessionid` statement was executed in the sys tenant, it could not terminate the SQL statement executed in a business tenant.

* Fixed the issue where, when the WHERE clause contained the `join` keyword in a string value, the partition information was incorrectly parsed, and the routing was inaccurate.

* Fixed the issue where, when an RPC proxy was used, the error `4016` was returned when inserting data into a single-partition table.

* Fixed the issue where, during manual partition splitting, ODP returned the error `-5627`.

* Fixed the issue where, during the initial phase of batch insert pressure testing, a large number of `routed to the wrong server` errors were returned.

* Fixed the issue where, after a node was restarted, the client disconnected and an error was returned.

* Fixed the issue where, when the ycsb tool executed the batch checkAndInsUp operation, the error `unknown errcode: -10652` was returned.

* Fixed the issue where, when a global index was queried, the error `OB_ERR_KV_GLOBAL_INDEX_ROUTE` was returned.

* Fixed the issue where, after migration, a global index returned the error `-5150` in ODP, causing the client to continuously reconnect and report errors.
