# OceanBase Database Enterprise Edition V4.3.5

## V4.3.5 BP1

### Version information

* Release date: September 22, 2025

* Version number: V4.3.5 BP1

* RPM version number: 4.3.5.1-42025091917

### Release purpose

Modify the default value of `enable_single_leader_node_routing` to `False`.

### Bug fixes

* Fixed the issue where the ODP memory leak stack print failed.
* Fixed the issue where executing an SQL statement starting with "hint" caused an ODP core dump.
* Fixed the issue where the table name in a DML statement being a keyword caused ODP to fail to parse the table name and trigger an abnormal exit.
* Fixed the issue where the column name in a DML statement containing the `#` character caused inaccurate routing.
* Fixed the issue where the getaddrinfo system call returning more than 64 IP addresses caused an ODP core dump during startup.
* Fixed the issue where repeatedly executing scan_all caused a disconnection.

## V4.3.5

### Version information

* Release date: July 16, 2025

* Version: V4.3.5

* RPM version: obproxy-4.3.5.0-282025071514

### Version location

ODP 4.3.5 is the latest version in the ODP 4.3.x series. It is recommended for cloud and on-premises business scenarios for POC testing and production. It supports string-type routing, column value derivation for partition keys, multi-statement transaction routing, and month function routing, enhancing core routing capabilities. It also supports session connection pools to improve routing performance in short connection scenarios. It actively detects and handles deleted configurations in MetaDB, enhancing configuration stability. It refines error logs when the maximum number of connections is exceeded, improving diagnostic usability. The RPC proxy optimizes single-partition table judgment logic, enhancing routing accuracy in OBKV scenarios. It adds multiple SHOW commands to display object information, improving monitoring capabilities and operational usability.

### Key features

#### SQL proxy

##### Enhanced routing capabilities

* String type routing

   OceanBase Database has added support for the String type, allowing key, range columns, and list columns partitioning methods. ODP V4.3.5 now supports accurate routing for String types.

* Column equality inference for partition keys

   ODP parses SQL to obtain routing information, but only supports partitioning conditions like `C1 = xxx` (where C1 is the partition key). It cannot correctly parse conditions that require column equality inference, such as `C1 = C2 and C2 = xxx`, and must randomly route. ODP V4.3.5 now supports column equality inference for partition keys, allowing it to accurately obtain partition key values and calculate partitions for statements like `C1 = C2 and C2 = xxx`.

* Multi-statement transaction routing

  For multi-statement transactions started with Begin/Start transaction (e.g., `begin; xx; xx; commit`), ODP supports routing based on the first SQL statement.

* Month function routing

   ODP V4.3.4 supports partitioning scenarios where the partition key is a function expression. It can identify partition table creation information and parse and convert function expressions in the partition key to ensure accurate partition calculation. ODP V4.3.5 now supports accurate routing for the month function.

* Optimized routing logic after hint parsing failure

   When SQL statements contain complex hints like `/*+index(db.lna_n_biz_lock_080 primary) */`, ODP cannot correctly parse routing information, leading to inaccurate routing. ODP V4.3.5 optimizes the parsing logic for SQL statements with complex hints, allowing it to skip hints and continue parsing partition information for accurate routing.

##### Session connection pooling

ODP, as a high-performance proxy for OceanBase Database, excels in long connection scenarios with excellent routing performance. However, in short connection scenarios, its performance is subpar due to two main reasons:

* Frequent TCP connection establishment and closure between ODP and OBServer nodes.

* Synchronization of Database and System Vars when ODP switches routing to OBServer nodes.

To enhance routing performance in short connection scenarios, ODP V4.3.5 introduces session-level connection pooling. This feature reduces the number of system calls like accept in short connection scenarios and minimizes the latency of frequent connections, ultimately achieving performance optimization.

##### Configuration stability

ODP supports multi-level configuration items at the global, cluster, tenant, and VIP levels. Cloud ODP periodically queries the configuration items issued by ODP to MetaDB and actively inserts and persists them at the VIP level when changes are detected. However, the current implementation only detects new and modified configurations, and cannot detect configurations that have been deleted from MetaDB. As a result, these "expired" configurations are not deleted, posing a risk of misuse. ODP V4.3.5 introduces the ability to actively detect and clean up configurations deleted from MetaDB, enhancing configuration stability.

##### Improved usability

OceanBase Database allows control of the maximum number of connections for tenants through various configuration items and system variables. When the maximum number of connections is exceeded, ODP's error logs all show `too many connections`, making it impossible to accurately identify which configuration item is exceeded. ODP V4.3.5 refines and differentiates error logs in the diagnostic logs `obproxy_diagnosis.log` and `obproxy_error.log`, enhancing diagnostic usability.

#### RPC proxy

##### Internal object maintenance commands

ODP RPC proxy involves many internal caches during request routing. If the cache expires or stores incorrect data, it can lead to various stability issues. Diagnosing these internal objects through logs is time-consuming and not suitable for production environments. ODP V4.3.5 enhances operational convenience by using the `show` command to display information about commonly used OBKV objects such as `rpcRequest`, `tabletGroup`, `globalIndex`, `QuerySync`, `TabletLS`, and `Ctx`.

##### Improved usability

ODP V4.3.5 adds statistical items such as RPC connection information and `net_entry` to the Prometheus port, enhancing the monitoring capabilities of the ODP RPC proxy.

##### Optimized logic for determining single-partition tables

ODP determines whether a table is a non-partitioned or single-partitioned table based on the value of `part_num`. However, it cannot distinguish between the two. In scenarios where a table is split into partitions, the default table is a single-partitioned table, but ODP may incorrectly identify it as a non-partitioned table. The `tablet_id` values for non-partitioned and single-partitioned tables are different. In OBKV scenarios, if the `tablet_id` is not properly filled (with a default value of `0` for non-partitioned tables), OceanBase Database will return an error. ODP V4.3.5 optimizes the logic for determining single-partitioned tables. When a single-partitioned table is incorrectly identified as a non-partitioned table, ODP will retry the operation based on the `OB_SCHEMA_ERROR` information returned by OceanBase Database and route the request as a single-partitioned table.

### Supported OceanBase Database versions

OceanBase Database 4.x, 3.x, and earlier versions are supported. The recommended ODP version depends on the OceanBase Database version you use:

* If OceanBase Database is 3.x or earlier, we recommend that you use ODP V3.2.11.

* If OceanBase Database is 4.x, we recommend that you use ODP V4.3.1 (LTS version).

ODP V4.3.5 supports multiple new features. If your environment depends on these new features, we recommend that you use the latest version, V4.3.5. If your environment does not depend on these new features, we recommend that you use the LTS version, V4.3.1.

### Bug fixes

* Fixed the issue where ODP encountered an out-of-memory exception when processing the response from an OBServer node, triggering a core dump during connection cleanup.

* Fixed the issue where inserting data into a table after dropping and rebuilding a table with the same name but different partition types resulted in a `-4002` error.

* Fixed the memory leak issue in the SQLMonitorInfo module.

* Fixed the issue where querying a range-partitioned table after changing the partition structure resulted in an error `4723`.

* Fixed the issue where, after dropping an OBI instance, the long connections from downstream requests were not released.

* Fixed the issue where ODP failed to perform a hot upgrade.

* Fixed the issue where, in a specified zone routing scenario, when switching to a specified zone, if the tenant had no traffic, the cache was not updated, leading to routing to the new zone failing.

* Fixed the issue where, in a read-only address scenario with replica-based routing, after replacing the machines in a specified zone, the newly online machines were blacklisted and could not be whitelisted.

* Fixed the issue where, when building a batch table query using LSOP, if all columns were obtained and decomposed into multiple LSOP requests for different log streams, the getOperationRow function reported an error.

* Fixed the issue where, when connecting to ODP using a Go client, the TestPrimaryAndGlobalIndexNoPartition query returned a `-4016` error.

* Fixed the issue where the OB_RPC_TABLE_IGNORE_FIELD feature consumed excessive memory.

* Fixed the issue where, when an OBServer node encountered an exception and could not return results, ODP's memory allocation was limited, preventing it from reading the backend results, leading to the inability to clean up partition sub-requests and the inability to recover the occupied memory.

* Fixed the issue where, in a dual-write scenario, when the OBServer node's response did not meet the specifications, ODP did not intercept the abnormal results, causing a core dump.

* Fixed the issue where, under the OceanBase 2.0 protocol, after ODP's memory allocation failed, the protocol parsing failed, mistakenly using the MySQL protocol, resulting in a `-4103` error.

* Fixed the issue where, when the connection whitelist validation failed, the diagnostic logs were not recorded in a timely manner.

* Fixed the issue where, in a partition split scenario, after a non-partitioned table was split into a partitioned table, ODP incorrectly identified the table type, resulting in a `-4002` error.
