# ODP Community Edition V4.3.3

* Version: V4.3.3

* RPM version: obproxy-ce-4.3.3.0-5

### Version location

ODP 4.3.3 is the latest version in the ODP 4.3.x series. It is recommended for use in POC testing and production environments, both in the cloud and on-premises. The SQL proxy now supports read/write separation between primary and standby databases, allowing cloud users to achieve this with a single connection string. This enhances the product's capabilities for primary/standby database scenarios. Additionally, the proxy has been optimized for routing in scenarios such as replication table routing and weak read routing within transactions, meeting the routing needs for special tables and specific scenarios. It now supports more character sets and collations, including utf16le, sjis, dec8, utf8mb4_german2_ci, and HKSCS. It also extends support for accurate routing of expressions such as to_days() and timestamp. The routing capabilities are now more comprehensive. Monitoring information has been enriched, including PS cache and routing details, improving diagnostic usability. Multiple protocol-related issues have been fixed, enhancing stability. For the RPC proxy, different authentication logic is now supported for cloud and on-premises users, improving the Auth authentication mechanism. New OBKV-Redis protocol commands have been added, and their processing logic has been optimized to improve performance. ODP 4.3.3 is now fully compatible with Rocky Linux 9.

### Key features

#### SQL proxy

##### Primary/standby database read/write separation

Currently, the cloud platform supports business disaster recovery between primary and standby clusters, but it lacks the flexibility of ODP. In addition to database switching, other scenarios require switching domain names. As the number of users of primary/standby databases in the cloud increases, it is necessary to enhance the product capabilities for primary/standby databases, supporting read/write separation and primary/standby switching through a single connection string.

ODP V4.3.3 introduces the primary/standby database read/write separation feature. It allows automatic login to the local primary and standby clusters without changing the user login connection string. It also supports automatic read/write separation between primary and standby clusters. To reduce cross-region bandwidth costs, a compression protocol is used between ODP and OceanBase Database.

The primary/standby database read/write separation feature is applicable only to the primary/standby tenant architecture of OceanBase Database 4.x. It supports the eventual consistency of weak read requests.

##### Enhanced routing

OceanBase Database Proxy (ODP) V4.3.3 is the latest version of the ODP V4.3.x series and is recommended for on-cloud and on-premises business in a proof of concept (POC) test or production environment. The SQL proxy allows an on-cloud user to enable read/write splitting between the primary and standby tenants by using one connection string, thus enriching the capabilities of the primary and standby tenants. Routing capabilities are improved in the following ways: replicated table-based routing and routing for weak-consistency reads within a transaction are optimized to meet your requirements for routing of special tables in specific scenarios; more character sets and collations such as utf16le, sjis, dec8, utf8mb4_german2_ci, and HKSCS are supported; accurate routing is realized for the `TO_DAYS()` and `TIMESTAMP` expressions. Abundant monitoring information such as the prepared statement (PS) cache and routing information improves the usability of diagnostics. Several protocol-related issues are fixed to improve stability. ODP V4.3.3 is fully compatible with Rocky Linux 9.

  The SQL proxy can now correctly route SQL requests in the utf16le, sjis, dec8, utf8mb4_german2_ci, and HKSCS character sets and collations.

* Optimized replication table routing

  Replication tables are suitable for read-heavy scenarios. Queries and reads on local replicas of replication tables perform best. Therefore, replication tables are generally routed randomly. However, within a transaction, if a replication table has been modified, random routing to a Follower node may result in reading outdated data. In ODP V4.3.3, when a replication table has been modified within a transaction, the routing strategy is optimized to route query requests for the replication table to the Leader node.

* Optimized weak read routing within transactions

  In a transaction, if a write statement or a SELECT FOR UPDATE statement has been executed, subsequent read statements must use strong read mode to read the uncommitted changes of the transaction. In this mode, ODP routes the read request to the Leader node. If the read request is set to weak read mode, it is randomly routed to a Follower node. In ODP V4.3.3, this logic is optimized to route weak read statements after write requests in a transaction to the Leader node using strong read mode.

* Extended support for accurate routing of more expressions: to_days() function, timestamp 'xxxxx' expression, and not in expression.

##### Enhanced diagnostic usability

* PS cache monitoring

  In the PS protocol scenario, if a client uses a large number of PS caches without closing them, it may occupy a significant amount of memory and lead to performance issues. These issues are difficult to troubleshoot. To improve the efficiency of troubleshooting PS protocol issues, ODP adds PS cache information to Prometheus monitoring, including the number and size of allocated PS caches. It periodically outputs this monitoring data externally and supports the SHOW PROXYPS internal command for SQL queries related to PS, including parsing results and memory usage. This improves usability.

  For more information about the SHOW PROXYPS command, see [SHOW PROXYPS](../../../660.odp-command/20.odp-proprietary-commands/400.show/1000.show-proxyps.md).

* Routing information monitoring

  ODP adds statistics on various routing scenarios to Prometheus monitoring, including the number of requests for routing within transactions, secondary routing, random routing after failed partition calculation, and routing requests for global index tables. This helps in troubleshooting routing issues.
